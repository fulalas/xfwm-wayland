Memory consumption optimization log
===================================

Every strategy tried goes here: what, result, kept or dropped.

Baseline (0.7.39, 2026-11-11, real session, 3840x2160, RSS after boot)
----------------------------------------------------------------------
xfwm-wayland          168 MB at scale 1, 228 MB at scale 1.5, 409 MB seen once
xfwm-wayland-helper    28 MB
labwc                  29 MB
xfwl4                 158 MB
Goal: below xfwl4, as close to labwc as possible.

How it is measured here
-----------------------
.local-build/test/run-compare.sh [ours|labwc]
  Headless 3840x2160 on the real GPU (GLES): empty, then xfdesktop + panel,
  then 4 windows, then scale 1.5, back to 1, all closed.
  Result in .local-build/test/out/compare-*.txt (RSS split by mapping).
.local-build/test/tools/memlive.sh
  Same split for the live session. Not run yet, so real hardware numbers
  after these changes are still missing.

Headless baseline (RSS, MB)      ours 0.7.39    labwc
  empty                               83           94
  desktop + panel                    150          159
  4 windows, scale 1                 156          164
  4 windows, scale 1.5               215          220
It matches the real session (168 / 228), so the test is trusted.
labwc is not lighter in the same conditions. The 29 MB figure must come
from a session without the Xfce desktop.

Where the 156 MB went
---------------------
  65 MB  client buffers (wl_shm) mapped into the compositor, mostly the
         xfdesktop wallpaper (two 3840x2160 images). 126 MB at scale 1.5,
         because GTK draws at scale 2. This is the scale 1.5 jump and most
         likely the 409 MB case (more or bigger windows).
  40 MB  libLLVM + libgallium pages (Mesa), touched once at start.
  25 MB  other library pages.
  20 MB  private memory: 11 MB heap + 5 MB anonymous, almost all Mesa GL.
         With the software renderer the whole compositor idles at 10 MB.

Strategies
----------
1. Helper runs only when needed.                                   KEPT
   Starts at boot, on an xsettings change and for an icon it has not seen.
   Exits after 10 s without messages (on the first run, 60 s after it
   started, so a theme that xfsettingsd pushes late at boot is still
   seen; the first version restarted those 60 s on every message, so it
   lived ~2 min after login). Icon paths are
   remembered in the compositor (dropped on icon theme change, checked
   with a stat, at most 256).
   Result: helper is gone most of the time (28 MB -> 0).
   Cost: first icon of a new app waits for GTK to start.
   Test: .local-build/test/run-helper.sh

2. Release client buffer pages after reading them.                 KEPT
   madvise(MADV_DONTNEED) on shared file mappings found in /proc/self/maps,
   only for pages /proc/self/pagemap reports as file-backed.
   The pages belong to the client, so nothing is lost; the next read maps
   them again.
   Not possible through wlroots buffers: looking one up locks it, and
   unlocking an idle buffer sends the client a release it did not expect.
   Result: 156 -> 86 MB at scale 1, 215 -> 87 MB at scale 1.5.

3. Release library pages no longer in use.                         KEPT
   Same pass, for read-only private file mappings (code and constants).
   /proc/self/pagemap tells which pages still come from the file; only
   those are dropped. Writable mappings are never touched.
   Result: 86 -> 25-35 MB.
   Known risk: if another thread unmaps a file mapping and the range is
   reused for private memory between the pagemap read and the madvise
   (microseconds), that memory is wiped. No thread here is known to do it.

   When 2 and 3 run (server/memory_trim.c), checked every 500 ms while
   frames are drawn, with two levels kept from the last pass (file pages
   before and after it):
   - 16 MB above the level before: new memory, release now.
   - 16 MB above the level after, once a wait has passed: busy buffers
     came back; release and double the wait (2 s up to 64 s), so busy
     buffers are released only a few times.
   - calm (at most 2 frames in 500 ms), 1 MB above the level after, and
     60 s since the last pass: routine release. When the screen goes calm
     this pass is scheduled, so an idle desktop gets it too.
   One pass takes 1-5 ms.
   History of this rule: the first versions waited for a calm screen
   (boot peak 196 MB for 4 s), then hid new growth during the wait after
   a pass (live session at 1.5x: 29 -> 172 MB for ~1 min; desktop starting
   during the wait: kept 60 s), and only frames started the timer (live
   session: 45-58 MB after closing all windows). Headless with the current
   rule: boot drops at 0.5 s, desktop starting 1.3 s in drops at 1.8 s,
   1.5x with a busy terminal peaks for under 1 s, two windows closed then
   idle drop from 34 to 23 MB at the 60 s pass. Terminal CPU unchanged.

   Boot peak (2026-11-11): the first version waited for a calm screen, so
   at boot RSS sat at ~196 MB for 4 s (wallpaper buffers + Mesa pages)
   before dropping to ~23 MB. Releasing on growth without waiting for calm
   cut that to ~0.3 s. It cannot reach zero: the pages are mapped when the
   buffer is first read, and releasing on every commit costs CPU (see below).
   On the real machine the peak still lasted ~1 min: the desktop started
   during the 2 s wait after the first pass, so the wallpaper was counted
   as in use until the 60 s pass. Fixed with the release-again-and-double
   wait above: with the desktop starting 1.3 s in, RSS drops at 2.6 s
   (headless). CPU over 40 s, old build vs this: terminal 2 updates/s
   19/19 vs 20/18 ticks, 50 updates/s 395/392 vs 401/398, gears 167/160
   vs 153/169 (noise).

   First versions, dropped:
   - every 2 s no matter what: +28% compositor CPU with a window that
     repaints twice a second (the buffer was dropped and mapped again
     each time).
   - code pages on every pass, full pass every 10 or 30 s: same problem,
     smaller.

4. malloc_trim(0) on each pass.                                    DROPPED
   No change (private memory stays at 20-22 MB).

5. glibc settings: MALLOC_ARENA_MAX=1, MALLOC_TRIM_THRESHOLD_=128k
   with MALLOC_TOP_PAD_=0.                                         DROPPED
   Under 0.3 MB.

6. Mesa settings: MESA_SHADER_CACHE_DISABLE, MESA_NO_ERROR,
   AMD_DEBUG=useaco, GALLIUM_THREAD=0.                             DROPPED
   Under 0.3 MB, one made it worse.

7. Vulkan as default renderer (OpenGL if Vulkan fails).    DROPPED
   Headless 4K, real GPU, 40 s, compositor CPU ticks (lower is better):
                                   OpenGL    Vulkan
     terminal, 2 updates/s           20        13-15
     terminal, 50 updates/s         400       288-296
     glxgears fullscreen 60 fps     152-159   119-130
   RSS: about 9 MB less (23 -> 14 MB idle with desktop and panel).
   Screenshots match OpenGL.
   wmbench on the real machine (4K 60 Hz, OpenGL -> Vulkan):
     desktop CPU        7.36 s -> 5.94 s   (-19%)
     energy             1930 J -> 1900 J   (-1.6%)
     average power      8.93 W -> 8.78 W
     windowed speed     372 fps -> 358 fps (-4%)
     frame to screen    16.68 ms -> 33.05 ms (one extra frame, every time)
   Dropped for the extra frame and the lower fps.

   Causes found (wlroots 0.20.2 source):
   - Extra frame: the Vulkan renderer has no render timer, so the "auto"
     render time had no budget and frames were drawn right after vblank
     instead of just before the next one.
     Try 1: render time from the GPU's done signal (output wait timeline).
     Still 32.99 ms. A timing log in a test build showed the wait never
     started (kernel refused the wait on all 1974 frames).
     Try 2 (kept): on renderers without a timer, use the CPU time to build
     the frame (0.4 ms, p90 0.6 ms) plus the 2 ms margin. wmbench, Vulkan:
     16.75 ms (16.82 ms with max_render_time=4), 368 fps windowed,
     1919 J, desktop CPU 6.62 s. OpenGL was 16.68 ms, 372 fps, 1930 J,
     7.36 s. Also used by HDR mode, which always runs on Vulkan.
     Try 3: wait for GPU completion again, without the flag the kernel
     refused. wmbench: 16.80 ms, but 357 fps windowed and 1947 J, back to
     the old Vulkan numbers (CPU-time version: 368 fps, 1904-1919 J). GPU
     completion likely includes waiting on the client's own GPU work, so
     the estimate grows and frames start too early. Reverted to CPU time.
     CPU samples are skipped for direct scanout frames (nothing drawn).
   - Lower fps: with no color setting, Vulkan draws every frame twice
     (16-bit buffer, then a full-screen pass). GPU time over 10 s, 4K
     headless: Vulkan two passes 270 ms, OpenGL 205 ms, Vulkan one pass
     105 ms. The one-pass path needs sRGB output, but wlroots decodes
     client pixels with gamma 2.2, so dark colors get darker (32 -> 26
     out of 255, 98% of pixels change). Dropped; the fps loss stays.

8. Make OpenGL as light as Vulkan on CPU (2026-11-12).          NOT DONE
   Profiled the compositor's main thread (perf_event sampler,
   .local-build/test/tools/sampler.c + profsum.py), 4K headless:
   - Busy GTK terminal: the client marks ~98% of the window as changed on
     every commit (GTK/VTE behaviour; the buffer is released 2.4 ms after
     each commit, so not caused by us). ~88% of compositor CPU is copying
     those pixels into the texture, with both renderers. OpenGL's copy
     (Mesa glTexSubImage) takes ~35% longer than Vulkan's.
   - glxgears through Xwayland: Xwayland commits ~3800 times/s (tearing
     hint, no frame pacing), waking the compositor ~3900 times/s for 62.5
     painted frames, with both renderers. OpenGL costs ~20% more here.
   Tried, 20 s runs (noise ~5%):
   - no OpenGL render timer: terminal ~-2%, gears ~0%.
   - keep the GL context bound (wlroots binds/unbinds it around every
     upload and pass): terminal ~0%, gears ~-7%.
   - MESA_NO_ERROR=1: ~-2%.
   - all three: terminal -4%.
   wmbench on the real machine, keeping the GL context bound vs not
   (same build otherwise): desktop CPU 6.88 s vs 7.37 s (-7%), energy
   1935 J vs 1907 J (within run-to-run noise), latency and fps the same.
   KEPT (only the bound context).
   Closing the gap needs a different upload path inside wlroots (zero-copy
   shm via udmabuf, or a persistently mapped upload buffer), i.e. patching
   wlroots.

CPU cost of the trimming (gears, 3 runs each, ticks): before 148-157,
trim off 154-157, only client buffers 154-157, all 156-159. Inside the
noise; at most ~2% at a steady 60 fps. Terminal tests: no difference.

  4 windows, scale 1                156       35
